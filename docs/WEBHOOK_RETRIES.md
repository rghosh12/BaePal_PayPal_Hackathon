# Durable webhook correlation retries

Run **`pnpm db:migrate`** before deploying the updated Node API/worker. Migration `004_webhook_retry_schedule.sql` adds attempt counts, due times, safe error codes, processing timestamps, a quarantine state and a due-work index. `server.ts` does not migrate automatically. Existing pending notifications become eligible; existing processed notifications are not reprocessed. The hosted mock Site is unchanged.

The HTTP boundary still requires verified PayPal Sandbox signatures before inserting a durable inbox row. This change does not weaken that boundary or treat notification payload amounts/status as payment evidence. Tests insert explicitly synthetic mock inbox rows; they do not prove real Sandbox signatures or callbacks.

The worker currently handles `PAYMENT.CAPTURE.COMPLETED` and `PAYMENT.CAPTURE.PENDING`. It binds usable order/capture references to a payment in the configured provider mode, fetches that payment's authoritative order and uses the existing capture verification before any financial transition. Provided capture IDs must agree with known/provider evidence. An approved order without capture evidence remains unresolved even if a notification claims completion. An authoritative pending capture can process a PENDING notification without recording completed funds; a COMPLETED notification waits for actual completed/refunded evidence.

Notifications that arrive before an order/capture ID has been persisted remain pending. Correlation misses, unavailable/invalid provider evidence and reconciliation errors are scheduled with exponential delays of 5, 10, 20, 40, 80, 160 and 300 seconds between attempts. Eight unsuccessful attempts move the row to **quarantined**, retaining its payload and fixed last-error code for operator investigation. Unsupported event types, malformed references, mode mismatches and conflicting capture references are quarantined immediately rather than silently processed or dropped.

Each tick selects at most 20 due rows ordered by due time, creation time and event ID. Retrying old unmatched rows moves them out of the immediately due batch so newer valid notifications can progress. Conditional updates require the same pending state/attempt count originally selected, preventing stale bookkeeping from reopening or overwriting a terminal/newer attempt. Provider calls happen outside database locks. This is not a distributed claim/lease implementation; overlapping workers can still issue duplicate read-only authoritative queries.

Safe `last_error` codes are `CORRELATION_MISSING`, `PROVIDER_UNAVAILABLE`, `PROVIDER_EVIDENCE_INVALID`, `PROVIDER_EVIDENCE_PENDING`, `RECONCILIATION_UNAVAILABLE`, `UNSUPPORTED_EVENT`, `MALFORMED_REFERENCE`, `MODE_MISMATCH` and `CAPTURE_REFERENCE_MISMATCH`. Provider exception text, credentials and financial payloads are not logged or copied into these fields. A processed inbox row means its supported notification was reconciled against authoritative payment state, not that a date is confirmed or a refund completed.

Refunded/reversed/denied capture notifications, checkout-order notifications and other event families are not implemented by this inbox handler. They remain quarantined with `UNSUPPORTED_EVENT`; do not interpret quarantine as proof that no funds moved. Existing payment/refund polling remains separate. Operator review/requeue tooling, retention/access policies, distributed leases, alerting and real Sandbox callback evidence remain in #7/#8. Repeated delivery of the same event ID keeps the existing HTTP inbox deduplication behavior; it does not reset an exhausted notification's retry budget.
